# D1 数据库迁移与回滚说明

本项目使用 Drizzle schema 生成顺序迁移，目标数据库为 Cloudflare D1。已经部署过的迁移文件必须视为不可变历史记录，不得重写、重命名或删除。

## 当前迁移

- `drizzle/0000_init.sql`：初始表结构。保留原样，不在其上直接追加修改。
- 后续 `0001_*.sql`：为现有用户、收藏和认证令牌表增加必要索引与外键约束。

`0001` 通过临时表重建两个子表并逐行复制数据，不修改 `0000`，也不主动删除孤儿数据。D1 默认执行外键校验；如果现有数据存在孤儿 `user_id`，迁移会失败并保留原表，必须先在 staging 审计和修复后再重试。

## 生成迁移

1. 修改 `db/schema.ts`。
2. 执行 `npm run db:generate`。
3. 检查新生成的 SQL，确认只包含预期的顺序迁移、索引和约束。
4. 将迁移文件和 `drizzle/meta/` 一起提交。

不要通过直接编辑已部署的旧 SQL 文件来“修复”线上结构。

## 应用迁移

在 staging 验证后，使用已授权的 Cloudflare 账号和对应 D1 数据库绑定执行迁移。执行前必须确认目标环境、数据库名称和备份/恢复点；本仓库不保存账号令牌或正式数据库 ID。

示例命令（需要用户在本机完成登录并替换占位符）：

```sh
npx wrangler d1 migrations apply <D1_DATABASE_NAME> --remote --config <wrangler-config>
```

## 回滚策略

D1 迁移采用向前修复策略，不为已部署迁移伪造 down migration：

1. 迁移前创建并验证数据库备份或恢复点。
2. 若新迁移有问题，先停止相关写入或回滚应用版本。
3. 对结构问题创建新的顺序修复迁移；对数据问题优先使用备份恢复或经审查的数据修复脚本。
4. 在 staging 复现、验证并记录影响范围后再处理 production。

禁止在没有备份、审批和目标环境确认的情况下执行 `--remote` 迁移。
